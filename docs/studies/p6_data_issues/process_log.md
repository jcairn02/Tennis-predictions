## 1. The request

* **The owner's words, verbatim** (14 Oct 2026). The owner pasted four findings from my P6 summary, then wrote:
  > "Find and fix these data gaps by either finding the data gap locally or on the web. Write up your discovery about this data. Clean up the data if its obvious and indisputable."

  The pasted findings (my words of 12 Oct, quoted back):
  > SofaScore has holes by period and draw. It has almost no Challenger point records from spring 2022 to the end of 2023, few for qualifying at any level, and about half for 2018 Challengers. P5's TennisLive pages fill most of these, so the rebuilt map now has point data for 94–99% of every cell P6 touched. Those TennisLive records usually lack the set-closing games.
  > Some of the map's own rows are wrong:
  > Tennis My Life misdates some editions (Nottingham 2025), and in 2021 it gives several consecutive Challengers at one venue the same name and date (six "Biella 1"s).
  > The WTA website records file 55 matches of September 2026 under the wrong WTA 125s. P2 should look at these.
  > Borrowed links remain a small known error. When SofaScore lacks a match, an event with a same-first-name opponent can take its place. A surname rule to stop this lost about 150 correct links (married names) to remove about 30 wrong ones, so I didn't adopt it. The link check flags these cases instead.
* **How it was read:**
  * Four issues, each to be (a) located in data on disk or on the web, (b) fixed where a fix is "obvious and indisputable", (c) written up.
  * "Fix" for the SofaScore holes means finding complete point records of those matches in another source, and collecting them if a source has them.
  * "Clean up the data" is bounded by the project's standing rules, which a general instruction does not override:
    * Stage 0's lower-level history (Challengers, qualifying, ITF, WTA 125) takes no change from a source other than Tennis My Life's own files without a candidate test ([13 Oct](../../decisions/2026-10-13-tml-lower-level-revisions.md); CLAUDE.md, "The frozen reference").

    * So fixes are applied directly only to what this session owns or what is descriptive (the gap evidence, its links, the data map). A fix that would change the model's tables is prepared and recommended, not applied.
  * Other readings, set aside: "fix" as only documenting (the owner asked to clean up); "fix" as editing Tennis My Life's or Sackmann's raw files (raw copies stay as served).
* **The target:** not a model study. No model result is read.

## 8. Weak points

* **The feed fix leans on the WTA API's player-matches file holding all 187 matches.** If a later file lost some, they would be missing rather than wrong, and TennisLive's rows, wired after the website source, would supply most.
* **A later version of the Kaggle copy** would bypass the fix: the ten ids would be absent, and a newly misfiled week would not be caught. Recommendation 3 (a blocking check) is the guard.
* **Builds made since the evening of 13 Oct carry the 41 misfiled matches.** That includes the template build of 14 Oct, which another session is fitting now. The effect is a few dozen women's lower-level results in September 2026, far below what any comparison resolves. It is not worth a rebuild by itself; the next build takes the corrected snapshot.
* **Subagent B's linking needs identical set scores.** Walkovers, retirements written differently, and team events (771 editions) were not judged, so a misdated edition made mostly of such rows would be missed. Only Tenerife was re-checked by the lead in full.
* **Where a flaw would most likely hide:** in a reader of the website copy this study did not find. A search of `src/` for the copy's folder finds three: `measure.load_wta_site` and `candidate_stage0.load_wta_site` (both fixed), and the WTA collector's seed list (`src/ingest/point_sources/wta.py`, `kaggle_seed_players`), which takes only player ids from the copy, not editions, so the misfiling does not touch it.
* **The ATP download's plan links targets to the copy by two surnames within 7 days.** A wrong link fetches another match's file. That is harmless, but the count of holes filled would be slightly overstated; staging should re-link by the files' own players and the official score.
* **The ATP files' served rate rests on 26 probes until the download ends.** Its summary (`infosys_challengers/summary.json`) gives the full rate.
* **A re-design** would read every source's edition purity weekly (A's TennisLive test), for every lower-level source the feed reads, not only the website copy. It would also probe every cheap source before writing an inference about it; the Infosys probe overturned this study's first draft.

**The Flashscore fetch (16 Oct):**
* **The links are the weak part, not the records.** `flashscore_coverage.py` linked by shared name words, first names included, over 18 days. The official check catches a wrong link only where an official row exists and the scores differ. Two ways a wrong link survives: the 153 links without an official row (placed on their surnames; one could be the same pair's other meeting), and a wrong link whose record happens to have the official score (no case found among the 16 agreeing links whose surnames differ, all read).
* **"Complete" is against Flashscore's own set score.** The official check compares the result, not every game; a record could hold every game of a wrong score sequence and still be called complete.
* **The amended rule costs about 6 right but incomplete records,** and the 7 unclear ones may hold more. They are listed in `link_vetoes.csv` with `surnames` true.
* **Where a flaw would most likely hide:** in the map's placement by frozen keys. 22 targets are no longer found by the key P6 froze on 12-14 Oct (re-dated or merged matches); their records are placed by the map's own linker or not at all, and the before/after counts leave them out.
* **A re-design** would link the copy's records with P13's surname rule plus the official score before fetching, and would key the map's placement on match ids rather than names and dates.
