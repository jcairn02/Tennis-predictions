## 6. Judgment calls and deviations

*(Placed before the chronology while the work runs; numbered in the order made.)*

1. **No plain decrypted copies** (before any request). The plan says "decrypt them at staging"; the AO/RG and backfill modules wrote plain JSON files, which for Court Vision would be about 7 GB for the tour level. The raw envelopes stay the complete copy; staging decrypts in memory. Other branch: plain copies, readable without the key derivation, at a cost in disk.
2. **Static first; the API only where the static file is missing** (after seeing Montpellier 2025's two MatchBeats copies). Options: (a) also fetch every match's API MatchBeats, which carries 8 more point fields and re-derived flags (about +20,000 requests, +16 hours); (b) the plan's design. Chosen (b): server, serve number, speeds, endings, scorer and scores are identical in both, and the plan names the static files. The number of matches whose static MatchBeats is in the older format is measured after staging and offered to the owner as an option.
3. **Court Vision given up after 3 codes without data** (`--cv-cold-skip-after 3`; other routes keep 8), after reading the 2018-21 backfill's receipts (every event with tracking had it for its first 8 main-draw codes) and the trial (Court Vision empty or absent at all 5 events). Other branch: about 5,000 more requests (about 3.5 hours), probably for nothing.
4. **The serve-speed expectation corrected, the run not stopped** (after the trial's checks). No trial event recorded speeds; ManTennisData, which copies these key statistics, times about 4,200 of the 24,961 planned matches (Masters about 95%, 250s and 500s 38% in 2025 and 52% in 2026, Challengers 44 and 733). The plan's "every point, its outcome and the serve speed" holds for those only. Rule 5's gate concerns what the trial reached (points), so the bulk goes ahead.
5. **Empty documents count as no data** (after Tokyo's 88-byte Court Vision answers): kept as served with their receipts, but they neither open a route at discovery nor reset the give-up count.
6. **The 17 Oct reset treated as a dropped transfer, and the run resumed** (21 Oct, after reading the daily collector's receipts). Options: (a) report and wait for the owner, as rule 2 does for a block; (b) resume. The plan's rule 2 names HTTP 429, a challenge page or an unexpected 403 as blocks; the feeds' client also stops at once on a reset. The host had served the daily collector every day since, and the owner had asked to "continue if this got interupted". Chosen (b), with the client now asking once more after a reset and stopping on a second in a row, so a host that really refuses still stops the run. The other branch would have cost more idle days.

## 8. Weak points

* **The trial's events were chosen by hand,** one per stratum, before any request; all five turned out to be events without speeds. The checks of speeds therefore rest on the bulk's first Masters event so far.
* **The empty-file threshold** (`EMPTY_BYTES` = 200) is set from one kind of empty answer (88 bytes). An empty document of another shape over 200 bytes would count as data and keep a route open; it would cost requests, not data.
* **Court Vision's give-up after 3** could miss tracking at an event whose final and semi-finals were played off the tracked courts. The backfill's 4 events and the trial's 5 do not show such a case.
* **The API-only fallback** asks the API only for codes whose static copy is missing; a static copy that exists but is in the older format is kept as it is (judgment call 2).
* **The daily collector's held files** are trusted as complete when its own staging marks the match complete; a file it fetched later and overwrote is not re-checked here.
* **Where a flaw would most likely hide:** the orientation of the key statistics' players against MatchBeats' (check C assumes they are the same order; the staging records both, and B orients by the key statistics' own players).
